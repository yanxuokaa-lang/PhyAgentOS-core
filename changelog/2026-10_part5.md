### 具体失败场景与现有机制不足 / Concrete Failure Scenario and Existing-Gap Analysis
- `object.place` 已取得成功终态并确认 release/retreat；随后 `scene.observe` 与 capability refresh 成功，只有 post-place 的只读理解 Query 返回 `status=unavailable`、`failure_stage=provider`、`provider_error_class=contract+transport`。因此这不是动作失败、未知物理效果或旧场景 Action 重放问题。
- Gateway 调用记录已落盘，但 `_planning_record_status()` 将语义 unavailable 投影为失败，`settle_node()` 随即生成 failed settlement，默认 recovery 再调用 `fail_task()`。失败 settlement 是 append-only 结算事实，事后简单返回 `blocked` 无法让同一节点重新 ready，因此必须在 settlement 之前分流 provider block。
- 版本号、主键、事务、类型和普通测试可以保护记录一致性，但不能表达“只读能力暂时不可用、任务仍可恢复、且 readiness 未变化前不得重试”这一运行态。此次只复用现有 Coordinator event/task 状态和 Tool readiness，不新增 hash、冻结 contract、baseline 或发布 gate。

### 架构与安全边界 / Architecture and Safety Boundaries
- Runtime 拥有 provider health/readiness 与 Query 结果；Gateway 拥有 invocation/result 真值；Coordinator 拥有 blocked 事实与任务持久化；PlanningLoop 负责暂停/恢复；Agent 仅在恢复后按正常治理路径重新选择参数。
- provider block 不生成成功证据，不打开任何后继节点；恢复前不重复同一 Query，恢复后仍需有效 Query settlement 才能继续绑定、规划或 Action。
- 不启动/停止 provider 服务，不执行 live Query/Action，不推进 simulator；所有测试使用 fake Coordinator、结构化 envelope 与可控 readiness provider。
