# Implementation Review v15.6.9: Provider Target Resolution Boundary

Date: 2026-10-22 (Asia/Shanghai)

## Findings First

### Major resolved: profile provenance could override measured binding

`LabUtopiaProfile.paos_input()` previously accepted measured entity and
destination references but retained profile observation, revision, frame,
calibration, and freshness fields. That could pair a new perception identity
with an old profile evidence chain. The profile now copies all provenance and
freshness fields from an explicit binding and rejects incomplete or stale
binding data.

### Major resolved: target identity had no replaceable provider port

The generic workflow now exposes `ManipulationTargetResolver` and
`resolve_manipulation_target()`. The port accepts only an opaque binding and a
request. It validates freshness and requires the resolved target to preserve
entity, destination, candidate, scene revision, frame, and calibration
identity. Isaac-specific `/World` paths remain inside the adapter result and
are never generated by the generic workflow.

### Remaining Blocker: the new port is not yet the normal subtask preparation path

LabUtopia currently injects the resolver into its legacy cycle preparation
provider. The standard `manipulation.execute_subtask` path still relies on the
caller-supplied `preparation_provider`; it does not yet compose the resolver
with `manipulation.prepare` and persist the resulting adapter route for
`object.acquire`/`object.place`. Therefore this phase proves the boundary and
legacy no-motion wiring, but not the requested full subtask execution.

## Architecture Review

- Generic PAOS owns the resolver protocol, identity/freshness checks, Tool
  lifecycle, receipts, and one `NodeSettlement` per subtask.
- The adapter owns scene-node lookup, coordinate conversion, and target fields
  that are not stable across environments.
- AgentLoop is unchanged and receives no intermediate model turn between
  internal Tools.
- No new hash, baseline, or broad gate was added. The freshness and identity
  checks protect a concrete failure: mixing a current object binding with a
  stale scene route; ordinary profile validation cannot detect that mismatch.

## Decision

The provider boundary is accepted as a no-motion architectural increment. The
overall laboratory task is not accepted as complete. The next implementation
must compose the resolver with the standard preparation provider, persist the
route in the assignment store, and prove one LabUtopia subtask settlement over
`acquire -> prepare_held -> pour/stir -> prepare_held -> place` before any live
execution claim.
