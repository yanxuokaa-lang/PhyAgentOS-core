## 2. 七个维度的可行性判断

| 维度 | 判断 | 依据与剩余事项 |
| --- | --- | --- |
| 架构集成 | 可行 | 原 CapabilityRuntime 支持注册端点与通用 Action 生命周期，无需第二循环 |
| 实现完整性 | 需四层联动 | 契约/投影、Runtime/worker、方法/计划、验证/部署缺一不可 |
| 配置与复现 | 可执行 | 版本、profile、资产、阈值、seed 和标签映射有明确记录位置；实际值在 P0/P2 确定 |
| 错误与可观测性 | 路径明确，待实现 | 原 poll/cancel/stop 与 unknown 对账可复用；新动作必须返回过程测量和当前持物结果 |
| 机器人安全 | 方案保留现有边界 | 当前状态、frame/calibration、碰撞、attached geometry、限位、停止都由原执行 owner 检查 |
| 可维护性与兼容 | 可控 | 新能力按 profile 装配，旧抓放来源保留；不引入实验室专用 Core 分支 |
| 验证充分性 | 设计可检验，物理未证实 | 有已有测试入口、新增测试位置和 12 回合工程矩阵；实际运行结果待实施产生 |

## 3. 关键风险的处理分支

### R1：细棒和杯内空间不可操作

优先检查资产尺度、夹爪包络、棒柄抓取区、杯口空间和工具变换。
可调整棒柄与支架、布局和接收容器可见性，并记录任务条件变化。
若只有真实玻璃细棒和透明自由烧杯才满足用户需求，应重新估计感知和操作成本，不能沿用简化场景的可行性结论。

### R2：持物状态与准备路线不一致

来源选择必须同时保留原 acquire 归属与最近一次真实操作结果。
抓取时准备的轨迹不能覆盖后来倾倒/搅拌后的状态；路线准备拒绝时，处理当前现场或调整操作方法。
不修改 preparation_ref 的字符串来假装新路线，也不通过放宽场景检查让旧路线通行。

### R3：场景简单，规划展示不足

给定试剂顺序是用户要求，应保持。首版用观测到的阻挡和暂存占用引出必要前置动作。
用户已确认阻挡变化；需验证清障前后抓取可行性，不能只展示物体摆在目标前方。
增加瓶数、动作时长或文字说明不能单独解决这一问题。

### R4：打包方式与方法选择不匹配

先检查现有安装机制；优先使用同一 Runtime 的实验室 profile。
独立方法加载尚不支持时，将方法组织进同一包，而不是先实施完整架构迁移或复制一个长期运行世界。
新的 Tool 在注册、上下文、打包和隔离安装全部一致后才进入实际任务能力列表。

## 5. 审核结论与本次验证

结论：修订后的计划适合进入分阶段实现；无液体、顺序操作的方案在架构上可落地。

F1-F11 已有明确责任层、实施阶段和验证方法；它们在代码和物理层仍需逐项完成。

本次验证仅针对文档：UTF-8、Markdown 围栏、本地链接与源码位置、测试入口存在性、
Git 空白检查和最新五版本日志一致性。没有执行新动作、部署、仿真或硬件测试。
实施阶段按计划给出的离线命令与后续实际仿真入口验证；结果保存后再作能力完成判断。
