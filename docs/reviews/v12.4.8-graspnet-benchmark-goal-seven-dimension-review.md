# v12.4.8 GraspNet score and benchmark-goal seven-dimension review

Date: 2026-09-30 (Asia/Shanghai)
Scope: no-motion implementation and release review for Skill 2.10.1 / Node 0.10.1.

## Findings first

- Blocker: 0.
- Major: 0.
- Minor: 1. The global Skill manifest still lists `manipulation.target` and
  `manipulation.staging` because Runtime readiness currently validates one
  profile-neutral required-tool set. In benchmark mode their live ToolSpecs have
  no planning capabilities and both endpoints return `benchmark_goal_only`. A
  model could still spend one read-only query on the compatibility endpoint, but
  it cannot create a destination or authorize motion. Profile-specific manifest
  required-tools remain a future cleanup, not an acceptance blocker.

## 1. Architecture integration

Pass. Native-score adaptation is located in the isolated GraspNet worker rather
than the provider-neutral Core. The Adapter accepts the internal diagnostic field
but projects only normalized provider-neutral candidates. Benchmark target policy
is enforced at the existing Runtime ToolSpec, Grounding preparation source and
Coordinator binding boundaries; no parallel planner or RGB-task special case was
introduced.

## 2. Functional correctness

Pass. Scores in `[0,1]` are unchanged, scores above one saturate to one, negative
scores are filtered and non-finite scores fail closed. Native-score ordering is
retained before sampling. In benchmark mode `task.goal` uniquely maps execution
identity to the externally injected destination. Agent-authored target/staging
references are overwritten by a unique benchmark goal or removed when mapping is
missing/ambiguous. Observation-owned mode retains autonomous target and staging.

## 3. Compatibility and extension behavior

Pass. Worker candidates without `native_score` remain valid, preserving GraspGen
and older worker compatibility. `goal_source=observation_owned` keeps existing
ToolSpec capabilities and target cache behavior. Benchmark behavior is selected by
the existing deployment profile field, so other tasks can opt into autonomous
goals without code changes.

## 4. Robotics safety

Pass. The change performs no Action and grants no motion authorization. Normalized
scores remain proposal ranking evidence only; preparation, workspace, collision,
IK, planning admission, Gateway and terminal-result gates are unchanged. An
occupied, unreachable or ambiguous injected benchmark destination fails closed
instead of creating a replacement pose. No Oracle geometry, fixed grasp template
or simulator pose was introduced into perception or grasp proposal.

## 5. AgentLoop, Coordinator and recovery semantics

Pass. Coordinator compilation treats persisted benchmark task goals as stable
task-definition facts and current scene binding as the identity correspondence.
It does not resend an invocation or manufacture an opaque reference. Ambiguous
goal injection removes `destination_ref`, causing normal selection validation to
stop the revision. Existing terminal settlement, outcome-unknown reconciliation
and post-world-change observation requirements are untouched.

## 6. Provenance and observability

Pass. The worker retains `native_score` beside normalized `score` for provider-side
diagnosis, while public candidates remain provider-neutral. Benchmark policy
rejections use stable code `benchmark_goal_only` and include `goal_source` in
diagnostics. Preparation re-queries Runtime-owned task-goal facts and matches both
`destination_ref` and bound execution identity, so a stale observation-owned cache
cannot silently win.

## 7. Tests and release readiness

Pass. Focused and release suites cover score saturation, negative/non-finite
values, native diagnostic compatibility, benchmark endpoint rejection, cached
target bypass, Runtime planning capability switching, unique goal override,
ambiguous goal fail-closed behavior and observation-owned compatibility. The
release suite reports 308 passed. Ruff, compileall and `git diff --check` pass.
Node 0.10.1 and Skill 2.10.1 build reproducibly from repository sources.

## Acceptance conclusion

Accepted for no-motion release. The original requirement is implemented: Agent
goal planning remains available as a general extension path, while the current
benchmark experiment takes placement regions only from externally injected
`task.goal` facts. A subsequent user-run RGB task is still required to prove live
GraspNet inference, complete Action settlement, final scene verification, video
manifest completeness and ForgeTaskVerifier success.
